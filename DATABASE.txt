NOTES
================================================================================================

MASTER vs TRANSACTION  (BRD section 6.4)
  Master tables are maintained through the admin panel Table Maintenance
  screens. Transaction tables never are — they are written only by the flows
  that own them: enquiry capture, registration, follow-up logging, payment
  collection.

RULES THE SCHEMA ITSELF ENFORCES
  students.inquiry_id      NOT NULL   no enquiry, no registration
  enrollments.inquiry_id   NOT NULL   the enrolment carries the same trace
  batch_albums             UNIQUE(batch_id)        one album per batch
  course_staff             UNIQUE(course_id, staff_id)
                                      a person teaches a course once, so
                                      promoting an existing teacher to primary
                                      must UPDATE the row, not INSERT another

RULES THE SCHEMA DELIBERATELY DOES NOT ENFORCE
  "at most one is_primary per course" — MySQL cannot express this as a plain
  constraint, so CourseService owns it at the service layer.

  batches.current_count is a cached figure. It is recomputed from enrollments
  on every registration and batch edit, never accepted from a form — a counter
  that drifts once stays wrong.

  inquiries.closure_reason_id is nullable in the schema but mandatory in the
  application whenever status becomes Lost or Not Interested, so a closed
  enquiry always carries a reason from the fixed list.
